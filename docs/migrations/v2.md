# Migrating to RPI v2

Version 2.0.0 keeps the repository name `cc-rpi` and makes Claude Code and Codex
native consumers of shared workflow sources. Migration is an explicit project or
user installation operation. This release does not update the owner's other
projects or install a recurring service.

## Invocation and layout changes

| Surface | Version 2 behavior |
| --- | --- |
| Shared instructions | AGENTS.md holds project facts and shared policy; CLAUDE.md imports it without a reverse import. |
| Workflow source | Portable `templates/skills/rpi-*/SKILL.md` plus declared references/scripts; generated native directories are complete packages. |
| Claude direct | `/rpi-research`, `/rpi-plan`, `/rpi-implement`, `/rpi-validate`; native `/plan` remains a mode. |
| Claude plugin | `/cc-rpi:rpi-plan` and the corresponding namespaced workflows. |
| Codex direct | `$rpi-plan` or the native skill picker from `.agents/skills/`. |
| Codex plugin | Native selector `cc-rpi:rpi-plan`, verified from the installed inventory. |
| Legacy aliases | Proven managed non-colliding aliases may retain explicit-only rename notices. No automatic forwarding; new installations add no aliases. |
| `plan` / `status` collisions | Remove only proven managed legacy files; preserve and report custom commands. |
| User lifecycle skills | Four workflows installed once at explicit user scope, with separate source/state receipts. Project detach leaves them intact. |
| Native packages | Native managers own immutable skill packages and version selection; the engine reconciles project content and direct fallback only. |

Claude's complete plugin does not filter individual domain skills. Use its direct
route for conditional domain selection. Codex's native module controls can select
domains. Never register duplicate direct and plugin copies of the same workflow.
See the [compatibility record](../compatibility.md) for tested client boundaries.

## Review and apply a migration

Use Python 3.11+ and a verified local source checkout. Bind `RPI_SOURCE` to that
checkout and `PROJECT` to the actual target's absolute path. Inspect the source
and prepare a local update plan, choosing the requested harness and route:

```bash
bash "$RPI_SOURCE/scripts/install.sh" --check
bash "$RPI_SOURCE/scripts/install.sh" --target "$PROJECT" --harness both \
  --route direct --action update --output "$PROJECT/.rpi/local/plans/v2-update.json"
```

Read the generated plan before applying. It reports source/target identity,
component selection, exact path/block/key changes, conflicts and recovery paths.
A `noop` needs no writes; a `conflict` blocks the operation set. Do not overwrite
an existing plan or infer ownership from a filename, heading or old sync receipt.
For a fresh target choose `--action install`. Select only needed optional domains
with the engine's documented `--domain` options.

A verified immutable v1 commit available in the source history can be supplied
with `--legacy-base`. Its exact bytes establish ownership only for known rendered
paths; a customized file or missing provenance remains project-owned. Preserve
strict release charters, project topology, private settings and custom aliases.
Review native capability changes separately using the explicit component IDs
listed in [native policy setup](../native-policy.md#project-setup-and-evidence).

After reviewing the concrete plan within the authorized scope:

```bash
bash "$RPI_SOURCE/scripts/install.sh" --apply "$PROJECT/.rpi/local/plans/v2-update.json"
bash "$RPI_SOURCE/scripts/install.sh" --check --target "$PROJECT" --harness both --route direct
```

The engine stores owned nonsecret baseline bytes under `.rpi/baselines/` and the
installation manifest under `.rpi/manifest.json`. Recovery preimages and journals
stay in ignored `.rpi/local/`. An unchanged source revision still detects damaged
installed files. Unknown settings and modified owned content are preserved.

For interruption, use the recorded transaction journal with
`bash "$RPI_SOURCE/scripts/install.sh" --rollback "$RPI_JOURNAL"` after binding
`RPI_JOURNAL` to its actual local path. Rollback rechecks current bytes and refuses
to overwrite concurrent edits. Retain a conflicting journal for reconciliation.
On tested macOS/Linux runtimes, a process-held advisory lock releases even after
forced termination. The empty lock file remains deliberately; do not delete an
active lock. A nonempty legacy lock is preserved for operator inspection rather
than automatically reclaimed. Recovery rechecks its journal and root binding
after obtaining the lock.
Detach uses the same plan/apply process with `--action detach`; it removes only
unchanged owned content and preserves customized files and curated artifacts.
In dual installations, shared runtime files remain owned by the surviving harness.
Each harness records its selected source separately, so updating or detaching one
does not retire resources still required by the other.

User installation is a separate request: `--scope user` defaults to
`~/.claude/skills`, `~/.agents/skills` and
`~/.config/cc-rpi/installations/user`. Do not run a user update merely because a
project update completed. Plugin cache updates/rollback belong to native managers.

## Policy evaluation now fails closed

The v1 `guard-bash.sh` wrapper could allow commands when its parser or dependency
failed. V2 intentionally changes guarded shell events to fail closed: malformed
input, missing policy prerequisites and unclassifiable policy-sensitive commands
produce `BLOCKED / WHY / FIX`. The shared Python policy runtime avoids a new jq
dependency. An ordinary unrelated tool is not blocked merely because it has no
shell command, and optional telemetry failures remain non-blocking.

Treat this as a compatibility change. Before applying an update, review its
ownership-aware plan and separate native permission diff. Verify the required
runtime and the actual harness registration and trust. Keep the suggested repair
visible when a prerequisite is missing; do not disable the guard to finish an
update or fabricate an approval receipt.

Claude native ask/deny rules and Codex native permissions are different adapters.
Do not copy Claude settings into Codex. Registration, trust and observed execution
are separate facts. In particular, a Codex hook can be enabled but untrusted and
therefore skipped. A `PreToolUse` hook cannot manufacture user consent; unsupported
approval output is not an approval boundary.

## Declare the project's complete verification selection

The portable runner is installed at `.rpi/scripts/rpi-verify.py`. Configure
`verification_checks` in the project's `.rpi/policy.json` from its actual full CI
selection, including applicable tests, coverage, typechecks, lint and builds.
Each entry has one unique `name` and a literal `argv` array. Also declare
`verification_command`, the command used to rerun that selection. These are
project facts reviewed during setup; they are never proof of user consent.

For example, a Node project whose CI uses these scripts can declare:

```json
{
  "schema_version": 1,
  "integration_branch": "develop",
  "remote": "origin",
  "verification_command": ["python3", ".rpi/scripts/rpi-verify.py"],
  "verification_checks": [
    {"name": "tests-with-coverage", "argv": ["npm", "run", "test:coverage"]},
    {"name": "typecheck", "argv": ["npm", "run", "typecheck"]},
    {"name": "lint", "argv": ["npm", "run", "lint"]},
    {"name": "build", "argv": ["npm", "run", "build"]}
  ]
}
```

Use the project's real commands and branch topology. Run
`python3 .rpi/scripts/rpi-verify.py` with Python 3.11 or newer. It runs the declared
checks sequentially, records every exit and binds the result to candidate bytes
and runtime metadata. A custom `--checks` run remains explicitly partial. The
publication policy requires the exact declared list and current passing evidence;
missing or changed declarations cannot reuse an old success. This repository
keeps `bash scripts/verify-local.sh` as its compatibility entry point.

Working-branch publication and Vercel Previews remain forbidden. Completed
integration and named-tag publication must satisfy the structural target and
local-evidence checks, plus the owner's authorization through a supported native
boundary. If that boundary is unavailable, remote automation stays blocked and
the release review provides exact commands for the owner to execute.

## Preserve local policy and model choices

Unknown or locally modified instructions, skills, hooks and settings remain
project-owned. Legacy sync metadata alone is not proof of ownership. The update
plan must preserve custom rules and native configuration ordering, with conflicts
visible before application. Repeated detach removes only proven owned content;
project facts, private values and unowned files remain.

The v1 settings template included the broad Claude allow entries `Bash(git *)`
and `Bash(gh *)`. Diagnostics reports those exact entries as
`legacy-broad-git-allow` and `legacy-broad-gh-allow`, with ownership unverified.
Matching an old template value inside mixed project settings does not establish
ownership. The lifecycle engine preserves such entries; review their removal
as a separate native permission setup diff while preserving unrelated settings.
This finding does not establish effective permission precedence or user consent.

Workflows now inherit the owner's active model and effort through omitted native
overrides. Old workflow-wide price tiers and generation pins no longer control
execution. [Optional economy launches and profiles](../model-profiles.md) are
explicit user choices. Native precedence can override or persist beyond an
invocation, so RPI does not silently switch the parent and promise restoration.
New installations leave experimental Agent Teams disabled; updates preserve an
existing explicit owner opt-in.

See [guardrails](../../methodology/ci-and-guardrails.md) for enforcement scope and
[model selection](../../methodology/context-engineering.md#model-selection--inherit-the-owner-pane)
for requested versus observed identity.
