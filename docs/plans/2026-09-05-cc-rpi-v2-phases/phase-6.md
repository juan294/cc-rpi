# Phase 6: acceptance and version 2.0 release preparation

[Main plan](../2026-09-05-cc-rpi-v2.md). Depends on Phases 1–5. Not batch-eligible. Outcome: a locally integrated, verified 2.0.0 candidate and reviewable publication package.

## Local acceptance matrix

Run the deterministic suite against three disposable adopter types: empty/main-only documentation repo; customized v1.29.0 project with partial Codex imports; and a small develop/main application fixture with deployment-trigger declarations. Exercise Claude-only, Codex-only and dual installation; domain-module inclusion/exclusion; update/no-op/conflict/detach; resource reachability; preserved project facts; aliases and native-name collisions. Include root-started and nested-started rule access, instruction-chain byte boundaries including markers, literal arguments, Agent Teams defaults and optional economy configuration. Use sanitized synthetic representations of the audit cases rather than changing real adopters.

Package from a clean local candidate and extract it outside the maintainer checkout. Revalidate Phase 2's selected plugin/direct routes and the documented direct fallback, including actual plugin namespaces and absence of duplicate registrations. Codex plugin support is claimed only if the early cc-rpi package test and final candidate evidence pass; otherwise document the tested native directory route. Lifecycle source resolution must work from its documented clone receipt or bundled package, with no unresolved placeholders. Let native managers own plugin updates/version selection; exercise cc-rpi reconciliation only for project-managed and fallback content.

Run filesystem/path/script cases on macOS and a pinned **local** Linux environment matching CI. New distribution/policy Python runtime support is 3.11+, tested at 3.11 and 3.13; record the exact environments. Use ordinary generated files where symlinks cannot be materialized, but do not claim native Windows support without testing it. No hosted runner is a platform-debugging substitute.

## Actual harness verification

Keep four claims separate: parse, load, invoke, enforce. A tool's zero exit, a file's existence, or a model saying it followed instructions is insufficient for all four.

- **Parse:** validate emitted metadata/settings with the correct consumers and project checker. A deliberately invalid disposable input must fail; the report must enumerate expected components. The no-op validator observed in research cannot be counted as coverage.
- **Load:** inspect actual fresh-session discovery/instruction events or native inventories. Confirm relevant skill IDs, resources, shared/adapter/nested constraints, and no unintended duplicate registrations. Check that retired managed `plan`/`status` aliases are absent and retained explicit-only aliases do not add model-facing descriptions. Record ambient plugins so they cannot accidentally supply missing functionality.
- **Invoke:** use `/rpi-plan` for direct Claude installation or `/cc-rpi:rpi-plan` for its plugin; use the actual Codex skill ID/selector flow discovered for the selected route (`$rpi-plan` for the native directory adapter). At least one interactive menu/selector check per CLI proves the user's invocation complaint is resolved. Test adapter argument delivery and one retained alias where supported. Headless ordinary-language interpretation alone does not prove this. Capture a transcript, event or screenshot as local evidence; this is bounded harness testing, not a revived desktop error-screenshot workflow.
- **Enforce:** verify native permission ask/deny and stateful hooks independently with harmless fixtures. For hook coverage, a forbidden fixture must reach the registered hook, be denied, and leave its execution sentinel absent; the allowed control must execute and create its sentinel. A model declining to attempt it or a different permission layer blocking it is not proof of the cc-rpi hook. Record the actual boundary and its supported execution modes; do not bypass a native deny merely to obtain hook evidence.

Use **16 short native smoke cases across Phases 2 and 6**: each harness runs research, plan, implement and validate on the primary profile (8); relevant and irrelevant natural-language trigger cases (4); research and implementation on a cheaper/lower-effort profile per harness (4). Two relevant cases run early for Phase 2's plugin decision. Reuse those results only where tested inputs remain unchanged; candidate changes invalidate the affected evidence and require a bounded rerun, with any expanded inference scope made explicit. Reuse cases for hook/loading and optional economy-helper evidence. Record observed effort, including Claude's session `CLAUDE_EFFORT` where exposed; separate requested model from observed model and mark the latter unavailable without a valid session-bound source. Do not force a guessed ID. Include a tiny meaningful TDD implementation and an intentionally seeded validation mismatch. These are compatibility checks, not a statistically reliable model benchmark.

Live CLI sessions consume inference. Their exact profiles and bounded case list must be within the relevant Phase 2/6 execution authorization; carry forward authorization already provided rather than asking again. Do not launch them during planning or silently expand into repeated optimization trials. Missing core Claude/Codex invocation or enforcement evidence blocks release, rather than being omitted from the result.

## Full verification and documentation

`scripts/verify-local.sh` must run the complete current/evolved CI selection: internal links; ShellCheck for all shipped changed shell plus the existing selection; count/ID/version/skill/drift checks; Python compilation and contract self-tests; new lifecycle/policy/renderer tests; JSON/YAML and native adapter validation; package extraction; install/migration preflight; measured changed-module coverage. Run required checks sequentially and aggregate every exit.

Coverage must distinguish measured line/branch coverage from contract/test counts. Reuse a single local suite result for its report; never convert three historical SELF-TEST PASS messages into coverage percent. Test Portfolio report construction/signing/delivery only against a loopback receiver with synthetic credentials. Preserve the hosted reporting contract without contacting the live endpoint during preflight.

Update README/GUIDE/setup/CONTRIBUTING, methodology indexes, release/migration instructions, CHANGELOG, version badge, `.claude-plugin/{plugin,marketplace}.json`, distribution metadata and self-application. State 2.0.0 support, namespaced invocation, retained aliases, model inheritance, local verification, v1 conflicts and rollback. Include the evaluated compatibility table and known unsupported integrations. Do not claim benchmark savings or that real fleet migration has happened.

## Main integration and remote boundary

1. Finish all phase changes locally and inspect the complete diff, findings coverage and artifacts. Preserve the plan and handoff. Recheck canonical main against the original integration base. If it moved, resolve and rerun invalidated/full required gates locally.
2. Integrate the completed v2 candidate locally into main, using fast-forward when available and a reviewed merge when necessary. Run the final full gate on that integrated state; bind evidence to its commit/tree and environment. Do not push a working/release branch or create a PR.
3. Prepare the concrete release review: candidate SHA, v2.0.0 notes, migration impact, local/actual-harness results, remaining support boundaries, and observed remote triggers. Inspect current remote deployment integrations read-only; local YAML cannot rule out an external Vercel connection. Any Preview trigger blocks pushing until a documented non-destructive bypass/disable is available.
4. Stop at the remote publication boundary unless the owner has already explicitly authorized this exact release scope. Main currently triggers Validate plus Coverage and its Portfolio report. Publication authorization must account for those effects and the named tag/release.
5. After authorization, push completed main once and observe its exact SHA/workflow/event/check set. If a remote-only failure occurs, diagnose and repair locally, then obtain any new required authorization; never enter an automatic paid retry loop.
6. After the required checks pass, publish only the annotated `v2.0.0` tag at the accepted main SHA and the reviewed release notes, within existing release authorization. A named tag-only push is separate from the single completed-main push, not an incremental code-debugging loop. Do not publish every tag, run a nonexistent registry-release step, or deploy production.

Local release readiness and remote publication are separate completion states. The implementation can deliver the verified local candidate while publication awaits authorization. Do not mark v2.0 publicly released before tag/release identity is read back. Cleanup removes only proven task-owned redundant worktrees after artifacts are preserved.
