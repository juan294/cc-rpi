# cc-rpi 2.0 implementation plan

Version 2.0 will make cc-rpi a reliable blueprint for **Claude Code and Codex**, with shared RPI instructions, native invocation, safe installation and updates, current executable recipes, and observable verification. It will preserve the workflow philosophy that has worked for the owner.

This is the final implementation direction synthesized from the Codex and Fable reviews and their subsequent critique. The source evidence remains local under `docs/research/`: `2026-09-05-rpi-blueprint-hybrid-review-codex.md`, `2026-09-05-blueprint-modernization-review.md`, `2026-09-05-code-skills-agents-catalogue.md` and `2026-09-05-code-skills-agents-inventory.csv`. Those ignored files are provenance, not dependencies required to use the published plan. The decisions below supersede conflicting proposals in those documents.

## Decisions

| Decision | v2.0 contract |
| --- | --- |
| RPI philosophy | Keep separate research, plan, and implementation-phase conversations; phase acceptance gates; TDD for behavioral code changes; and resolution of confirmed actionable findings before phase acceptance. An explicit user instruction can authorize continuation as it can today. |
| Completion | Complete the authorized phase, review, repair, simplify, and verify before its acceptance gate. Remove equivalent pre-edit/pre-verification approvals inside that phase. Preserve production, publication, destructive-action, and new-scope boundaries. |
| Verification | Targeted checks during edits; complete applicable local gates at phase acceptance and final integration. Reuse valid evidence for unchanged tested inputs rather than rerunning merely to write a report. |
| Agent assignments | Choose bounded independent assignments within the current phase from uncertainty, file ownership, available tools, and resource contention. Preserve domain coverage and the three-implementer ceiling as an upper bound, without a minimum team size. Fixed four/eight-agent counts stop being required. |
| Shared source | Portable canonical SKILL.md bodies plus two small declarative harness adapters. Generate each harness's installed files; do not hand-maintain two workflow bodies or assume Claude fields control Codex. |
| Invocation | Namespaced `rpi-*` workflows. Direct Claude installs use `/rpi-plan`, its plugin uses `/cc-rpi:rpi-plan`; direct Codex installs use `$rpi-plan` or its skill selector. Record the actual plugin skill ID on Codex. Native `/plan` remains a mode, not the blueprint artifact workflow. |
| Model selection | Inherit the deliberate pane/session choice by default; offer an explicit economy policy for mechanical workflows/helpers using supported native model/effort fields. Recommend Claude `best` with `high` for research/planning; centralize optional Codex profiles. No silent promotion or optimizing router. |
| Instructions | Shared project intelligence in AGENTS.md; CLAUDE.md imports it and adds only Claude-specific information. Scope optional procedures and domain knowledge to their actual tasks. |
| Remote budget | Working branches/worktrees remain local. Finish local verification and integration before the single authorized integration push. Never create Vercel Previews. Production remains separately authorized. |
| Distribution | Test plugin-first delivery in Phase 2 before sizing the lifecycle engine. Prefer verified native package management for immutable shared skills; retain ownership-aware handling for project instructions/settings, custom v1 files and direct-install fallback. Never three-way merge a plugin cache. |
| Release scope | Ship corrected canonical content, both native adapters, safe v1 migration, enforcement checks, and documentation together as 2.0.0. Individual phases are local integration milestones, not partial remote releases. |
| Project rollout | Test synthetic fixtures and isolated snapshots of representative adopters. Do not modify all projects under ~/code or run their updates automatically. The later fleet rollout is a separate operation. |

“Fix everything” remains an acceptance discipline: verify findings, fix confirmed actionable defects, and reject false positives with evidence. If a finding requires a new architectural decision, use the existing explicit exception and record it locally; do not silently discard it or create external issues without authorization. Optional lightweight workflows, blanket TDD relaxation, and removal of phase conversations are outside v2.0.

## Product architecture

Keep the repository/package name `cc-rpi`; describe it as **RPI for Claude Code and Codex**. Reuse the existing repository and distribution machinery rather than introducing an orchestration platform.

Proposed new/changed paths are implementation targets, not files installed by this planning task:

```text
templates/
  skills/<name>/SKILL.md          canonical portable metadata and instructions
  skills/<name>/references/       resources shipped with each selected skill
  rules/                         canonical universal and path-scoped constraints
  adapters/claude.json            Claude-only metadata and invocation rendering
  adapters/codex.json             Codex sidecar/config mapping
  distribution.json              component IDs, scope, dependencies, aliases
  AGENTS.md.template              shared project contract
  CLAUDE.md.template              import plus Claude-specific additions
  hooks/                         small native event adapters
  scripts/rpi-distribution.py     deterministic render/sync/check engine
  scripts/rpi-policy.py           shared supported policy checks
scripts/install.sh               compatible user-install entry point
scripts/verify-local.sh          one local CI-equivalent entry point
tests/                          lifecycle, adapter, policy and negative fixtures
```

The renderer produces full native skill directories, including references and scripts. Shared bodies have one authoring source; adapter metadata changes only harness semantics. Direct self-application uses cc-rpi's `.claude/skills` and `.agents/skills`, checked against a fresh temporary render. If self-application selects the proven plugin route, suppress equivalent direct registrations instead of exposing both. Existing valid symlinks may remain where outputs are byte-identical; a whole-tree `.agents -> .claude` link is not the default. Preserve the local Drawio skill as an explicit local extension; do not add it to exported domain skills accidentally.

Rules are manifest components too. Universal invariants render once into shared AGENTS. Claude keeps native path-scoped rule loading; Codex receives a short root rule map with essential invariants and conditional references to installed rule resources. Nested instruction files are optional mapped conveniences, not equivalent loading mechanisms. Phase 2 defines the exact mappings and a managed root budget of 8 KiB; diagnostics also account for the actual full instruction chain and configured limit.

The manifest defines **20 RPI workflows**: the existing 19 with an `rpi-` prefix, plus `rpi-assess` for evaluative/current-practice research. Keep `rpi-research` descriptive. Preserve the 12 current domain skill identities and conditional selection, plus the Codex-only simplify helper. Direct installation puts the four lifecycle workflows at user scope and the other 16 at project scope; plugin scope follows the verified native package mechanism. Avoid installing the same lifecycle name at both scopes/routes. Counts are derived from the manifest and tested; they are not inferred from copied prose.

Each project receives `.rpi/manifest.json` and non-secret content-addressed baselines under `.rpi/baselines/`. These record component ownership and prior rendered bytes, not credentials or entire user settings files. `.rpi/local/` holds ignored staging, recovery receipts, and transient diagnostics. Installation, update, and detach share this ownership model. Hashes without recoverable baseline bytes are insufficient for three-way reconciliation.

Direct user lifecycle installation has separate state at `~/.config/cc-rpi/installations/user/`, owning only the explicitly selected Claude/Codex user skill roots. It is never stored in an arbitrary project's manifest. Project detach cannot remove that shared installation. Plugin caches have native package ownership and do not receive cc-rpi baselines or merge journals.

Legacy Claude command entry points, except `plan` and `status`, may become managed explicit-only forwarders for existing installations during the 2.x compatibility period. The two colliding names are discontinued with a migration notice; custom commands remain user-owned. New installations use namespaced skills. Plugin invocation is separately documented, for example `/cc-rpi:rpi-plan`. Do not bulk-delete `.claude/commands` or mechanically rewrite `.Codex` paths.

## Release acceptance

Version 2.0 is ready only when all of these hold:

1. No active exported workflow recommends working-branch publication, Preview creation, or hosted debugging loops. Actual release topology and production authorization remain explicit.
2. Every manifest component and dependency exists; generated outputs validate non-empty coverage, portable metadata, actual bundled references, and expected native invocation. No unresolved installation placeholders or machine-specific paths appear in the published package.
3. Fresh installation, unchanged update, conflicting update, interrupted update, rollback, and mixed-ownership detach pass deterministic tests. User content/settings survive. Existing installation damage is detected even when the upstream revision is unchanged.
4. Fresh Claude and Codex sessions invoke the correct RPI skill, read its bundled resource, honor the phase boundary, and demonstrate the expected model/effort provenance. Native hooks demonstrate both an allowed event and a harmless denied event with matching receipts. A parser pass or success with zero inspected files is insufficient.
5. Phase workflows retain TDD, acceptance gates, durable handoffs, finding coverage, and complete local verification. Domain/tool facts remain available when relevant. No performance claim is made without task measurements.
6. cc-rpi and representative clean/legacy adopter fixtures pass the entire local CI-equivalent selection, including coverage-producer semantics and syntax checks. macOS and local Linux behavior are exercised; missing execution evidence is reported as a release blocker, not replaced by an assumption.
7. The version, plugin metadata, setup guide, migration guide, rule/error ledger, generated counts, and compatibility table all agree on 2.0.0 and actual supported behavior.
8. The complete candidate is integrated locally into cc-rpi's canonical `main`, and final gates bind to that integrated state. Remote publication remains pending explicit owner authorization.

Preserve curated plans, phase files, decisions, and handoffs as versioned project knowledge. Keep raw machine inventories, telemetry, and operational evidence local according to visibility policy. For cc-rpi, Phase 1 adds explicit tracking exceptions for this approved plan set and its handoff, while keeping the existing machine-specific research audit files ignored; rewrite AGENTS.md to describe that actual policy. Do not change ignore rules and then stage entire research directories.

## Release and support boundaries

Research and planning start from `main` at the baseline above. Implementation uses a local v2 integration branch/worktree and local child worktrees as useful. Do not push phase branches or create PRs. Before local main integration, check that main has not moved; resolve/revalidate locally if it has. Do not clean up a worktree until its source changes, plan, handoff, and evidence are preserved.

The currently inspected workflows run Validate on main pushes and PRs, and Coverage on main pushes, a daily schedule, and manual dispatch. Coverage also publishes a report to Portfolio. The release checklist must re-inspect these triggers at the final candidate. There is no authorized remote action in this planning request. A later approved publication may push completed main once and publish only the named v2.0.0 tag/release; it must not become a fix-and-repush debugging loop.

Initial tested harness targets are the observed Claude Code 2.1.261 and Codex CLI 0.153.4. The release records versions actually exercised; it does not promise every older client, transport, operating system, or third-party model provider. Core adapters must work with those supported clients before v2.0 can ship. Experimental workflows, advisor orchestration, cloud scheduling defaults and automatic model selection remain deferred. Phase 2 tests Codex consumption of the actual cc-rpi package: a verified plugin route becomes preferred for immutable managed skills; otherwise native directory installation remains supported with the limitation documented. Preserve the existing Claude plugin route. The engine manages project state and legacy migration in either case.

## Start and finish conditions

Start implementation with Phase 1 in an isolated local worktree. This document contains no unresolved product decision or permission request. Technical discoveries that invalidate a contract require a documented plan adjustment before dependent work, not an improvised bypass.

Finish each phase with: local commit identity, touched components, applicable test results, deviations with rationale, confirmed finding disposition, and the next phase's entry conditions. Save the handoff outside disposable worktree-only state. The final owner review should receive a locally verified 2.0 candidate, a migration demonstration, and a concise release summary—not another research exercise.
