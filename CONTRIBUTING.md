# Contributing to cc-rpi

Thank you for your interest in improving cc-rpi! This repository is a living document — it gets better every time someone encounters a new pattern, discovers a better approach, or finds a gap in the methodology.

## How to Contribute

### Reporting a New Error Pattern

If you've encountered a recurring Claude Code agent error that isn't in the catalog:

1. Open an issue using the **Error Pattern** template.
2. Include: the symptom, root cause, correct approach, and what to avoid.
3. Keep it generic — no project-specific references.

For the owner workflow, prepare the change locally:
1. Add the detailed entry to `patterns/agent-errors.md` following the existing format.
2. Add a one-line pointer to `patterns/quick-reference.md`. That file is an
   **index**, not a catalog: the rule body itself goes in the skill, rule file,
   or command that needs it, and the index line names where it went.
3. Update any hard-coded counts or references in onboarding docs and
   skills. Run `templates/scripts/verify-counts.sh` rather than grepping by
   hand — it computes the counts from the catalogs and reports every location
   that disagrees.

### Proposing a Methodology Improvement

If you've discovered a better workflow, a new best practice, or a refinement to an existing phase:

1. Open an issue using the **Methodology Improvement** template.
2. Describe what you learned, how you validated it, and where it fits in the methodology.

For the owner workflow, prepare the change locally:
1. Add or modify the appropriate file under `methodology/`.
2. If it's a new topic, create a new file and update `methodology/README.md`.

### Retiring a Rule or Error

Rules and errors can also come out, not just go in. A rule or error is a
retirement candidate on one of five grounds:

- **Superseded** -- another rule covers it completely.
- **Hook-enforced** -- a registered, trusted native boundary is observed blocking
  the behavior on the stated client version.
- **Model-native** -- reproducible cross-profile evidence supports the capability;
  one successful session is insufficient.
- **Merged** -- folded into a broader rule.
- **Harness-fixed** -- version-bound native/tool evidence shows the failure no
  longer applies within a precise scope.

See the full procedure, non-candidate criteria, and the Retirement Ledger
in [.claude/rules/contributing.md](.claude/rules/contributing.md). Keep permanent
IDs, successor references and unproven safeguards; there is no retirement quota.

### Consistency Sweep for Workflow Changes

If your change affects workflow, topology guidance, commands, rules,
skills, hooks, or onboarding instructions, include a consistency sweep
before merging.

Check these layers together:

1. `methodology/`
2. `templates/`
3. Generated Claude/Codex outputs and both `.claude/skills/` and `.agents/skills/`
   self-application; preserve extensions listed in `.claude/DIVERGENCE.md`
4. `CLAUDE.md` and `AGENTS.md`
5. `README.md` and `GUIDE.md`
6. `CHANGELOG.md`

Regenerate from canonical source and run the complete local gate below. The
manifest and drift checks catch missing resources, stale output and divergent
self-application that a prose sweep can miss.

### Improving Templates

If shared instructions, the setup checklist or native workflows could be better:

1. Prepare changes to files under `templates/` in a local worktree.
2. Explain what problem the change addresses.

### Canonical source and generated ownership

`templates/distribution.json` declares component IDs, selection, resources,
ownership and adapters. Edit canonical `templates/skills/` bodies and their
declared resources, then render `generated/claude/` and `generated/codex/`.
The Codex-only `codex-simplify` source stays under `.codex/skills/`. Do not edit
generated bytes, native caches or installed copies to change the blueprint.

This repository self-applies complete generated skill directories through
`.claude/skills/` and `.agents/skills/`. Shared facts and managed universal rules
live in AGENTS.md; CLAUDE.md imports it. Conditional rules retain their explicit
task/path mapping. [.claude/DIVERGENCE.md](.claude/DIVERGENCE.md) records remaining
compatibility links and local extensions, including the project-owned Drawio
skill. Preserve those extensions and adopter-specific release obligations.

Native directories may use matching copies where symlinks are unavailable;
legacy compatibility links have their own drift rules. Consult
[compatibility evidence](docs/compatibility.md) for tested platforms. Neither
successful rendering nor source portability proves native Windows execution.

### Local verification

Use Python 3.11 or newer and Git, Bash, ShellCheck, Node, gh, uv, OpenSSL and curl.
Install the pinned Python dependencies in a task-local environment:

```bash
python3 -m venv .rpi/local/venv
.rpi/local/venv/bin/python -m pip install PyYAML==6.0.3 coverage==7.16.0 uv==0.12.10
source .rpi/local/venv/bin/activate
```

With that environment on PATH, regenerate and verify:

```bash
python3 templates/scripts/rpi-distribution.py render
bash scripts/verify-local.sh
```

The gate runs the declared CI selection sequentially: prerequisites, internal
links, counts, version, native skills, self-application drift, shell lint, syntax,
unit/contract tests and measured line/branch coverage. Its evidence binds source
bytes and runtime identity; a later success cannot hide an earlier failure.
Behavioral changes require a meaningful regression that fails before the fix.
Release acceptance also requires the applicable native, extracted-package and
disposable-database checks recorded in the compatibility report.

Lifecycle changes must preserve file/block/settings-key ownership, recoverable
baselines and transaction journals. Exercise custom adopter data, conflicts,
interruption and rollback; never relax a local release charter to make an update
pass. Registration, native trust and observed enforcement are separate evidence.

## Local Integration and Contribution Guidelines

Owner working branches/worktrees stay local. Run the complete local gate with
`bash scripts/verify-local.sh`, integrate locally, inspect hosted triggers, and
push completed integration once only within explicit authorization. Never use
Vercel Previews or hosted CI as a debugging loop. External contributors may use
GitHub contribution channels; agents do not publish working branches or open
issues/PRs without the applicable authorization. Production is a separate release.


- **Keep PRs focused.** One pattern, one improvement, one fix per PR.
- **Keep entries generic.** No project-specific references, company names, or proprietary details.
- **Use file:line references** instead of code snippets in documentation — snippets go stale.
- **Test your patterns.** If you're adding an error pattern, confirm the solution works across at least two sessions.
- **Follow existing format.** Match the structure and tone of existing entries.
- **Sweep all documentation layers** when workflow guidance changes.
  Don't update a template without checking the repo-local copy and
  onboarding docs.

## Commit Messages

Use conventional commits:

```
feat(patterns): add new error pattern for X
fix(methodology): correct phase 2 process step
docs(templates): clarify CLAUDE.md authoring guidance
```
